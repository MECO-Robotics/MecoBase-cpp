# Recording and replay

The library records one versioned `Replay/Frames` JSON record per robot cycle in the primary WPILOG. The file uses the AdvantageKit WPILOG header and includes timestamped typed `ReplayInputs` and `ReplayOutputs` entries for AdvantageScope and other WPILOG readers.

Build metadata records the current Git revision and checkout dirty state. `buildSourceHash` covers production sources (`src/main`), vendordeps, and `build.gradle`; test-only edits do not change that hash.

A consuming robot integrates replay at its lifecycle boundary: install recorded Driver Station state and FPGA timestamps before running its normal mode callbacks, scheduler, commands, and IO-owned mechanism controller emulation. The installed FPGA timestamp is the replay clock, so normal `frc::Timer::GetFPGATimestamp()` reads and command waits advance with recorded frame time. Those clock reads do not need separate `ProcessInputs` entries. The framework does not feed recorded actuator outputs back into the code. New outputs go to a new WPILOG.

Use `ProcessInputs` for structured input snapshots and `ProcessValue<T>` for a single typed setting sampled at a behavior boundary. `ProcessFileInput` captures bounded text asset bytes for consumers that can parse from memory. `ProcessNavigationGridInput` applies that boundary and parses a PathPlanner occupancy grid. The native Base ADStar loader reads its navgrid through a bounded file input at the first pathfinding request. `VerifyFileInput` and `VerifyDirectoryInput` capture file contents for replay consumers that parse from bytes. `VerifyPathPlannerAssets` records bounded file manifests for the standard PathPlanner and Choreo deploy directories once per process session, at its first in-frame use, then fails replay if any path, size, or content hash differs. The manifest avoids placing complete deploy trees into a single frame. PathPlanner's name-based loaders still read from disk, so the manifest check does not reconstruct their assets from recorded bytes; the native ADStar navgrid and scheduled Choreo trajectories do consume recorded bytes. Keep asset checks at the point the asset affects behavior; static setup that runs before a frame cannot be recorded there. `base/ReplaySettings.h` provides typed Dashboard, Preferences, NetworkTables, and battery-voltage reads through that replay boundary. `ProcessValue` records the value under `Replay/Inputs` and mirrors the effective value under `Replay/Outputs`; dashboard, Preferences, and NetworkTables values remain operator configuration during live operation. `RecordedInput` reads a required value from the active frame and fails if called outside a frame or if the input is missing. `base/TelemetryPublishers.h` provides asynchronous typed Dashboard and NetworkTables publishing. Each consumer must still route every behavior-affecting setting and season decision through these APIs. Directly reading a setting during replay is not deterministic.

Driver input is captured after Base resolves the selected NT or USB axes, fallback policy, and teleop/E-stop authority. Code replay consumes that resolved `Input/DriverInput` snapshot instead of polling live joysticks or recomputing source selection. `base::FollowChoreo` reads the trajectory bytes through `ProcessFileInput` when scheduled and parses the captured data. Object detection frames are captured by `ObjectPerception` at each camera read boundary, including empty-frame samples, sequence numbers, capture timestamps, and camera-relative points. Replay restores those frames without opening a live NetworkTables subscriber. SystemCheck also records its dashboard start/abort/arming inputs and battery/brownout interlocks, records live measurement and status outputs, and publishes dashboard measurements and status through the asynchronous telemetry worker; Driver Station attachment, mode, and E-stop state come from the replayed Driver Station frame.

The reusable `base::ReadDriverStationMatchInfo()` API provides enabled, autonomous, teleop, test, alliance, remaining match time, and game-specific-message inputs through `ProcessInputs`. Native Base recordings capture that full snapshot. The replay adapters accept Java AdvantageKit 26.0.2 logs for the documented drivetrain and Driver Station schemas. Java logs map enabled/mode/alliance fields, but their supported Driver Station schema does not include remaining match time or game-specific data; those values remain unavailable during Java-log code replay. The Java log does not identify the C++ drivetrain backend, so configure `FRC_DRIVE_BACKEND` when it differs from the consuming robot's default. The Java adapter exposes its SmartDashboard auto chooser value as the opaque `Auto/Selection` input; each robot must map a recognized label to its own stable autonomous ID. Other Java mechanism, vision, and device IO schemas must be mapped by the consuming robot; replay must not read live devices as a fallback. Season-specific decisions and results still need consumer-owned `RecordOutput` calls.

AdvantageScope can open either log for normal playback; code replay is a separate operation. WPILib NT topics are stored with an `NT:` prefix in WPILOG. Each recorded cycle also exposes timestamp-aligned JSON snapshots at `Replay/Inputs` and `Replay/Outputs`; `Replay/Frames` remains the authoritative replay source. `Replay/RecordingStatus` is sampled once per second and finalized at orderly shutdown. Periodic snapshots may lead or trail persisted frames because status and frame records are not synchronized with the lower-priority writer; readers require an exact count from finalized status records.

For the C++ to Java format-compatibility probe, run `tools/akit-acceptance/verify-cpp-writer.sh`. It generates a fixture through the library's native test and reads it with the Java AdvantageKit 26.0.2 reader from the sibling Java project. This checks selected typed values and timestamps; it does not establish full robot replay equivalence or hardware behavior.
